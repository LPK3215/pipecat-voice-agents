# 第二阶段：在框架上写自己的业务

> **第一阶段**（`HANDBOOK.md`）：把语音链路跑通，搞清楚四个模型插槽怎么换。
> **第二阶段**（本文）：把「能聊天的语音助手」变成「能干活的东西」。
>
> 两阶段的边界很清楚：
> **第一阶段改的是「怎么听、怎么答」；第二阶段改的是「答什么、去哪拿数据、做完什么动作」。**
>
> **语言约定（本文与全部配套文档适用）**：文档正文用中文；**代码、命令与终端输出一律按
> 原文展示（英文纯 ASCII）**，不做中文意译。例外：提示词、工具 `description` 与 `spoken`
> 朗读文案属于**功能内容**，示例代码里出现中文是刻意的（本手册第 2 节就有）。

## 0. 第二阶段到底做什么

一句话：**给模型接上工具和数据，让它能查、能算、能干。**

不变的部分（第一阶段已完成，基本不用再动）：

- 语音链路：VAD → ASR → LLM → TTS
- 传输层、打断处理、每轮延迟统计
- 四个模型插槽

变化的部分：

| 要素 | 第一阶段 | 第二阶段 |
|---|---|---|
| 工具 | 1 个示例（查时间） | 你自己的业务工具 |
| 数据 | 示例数据 | 你的真实数据 |
| 编排 | 单轮问答 | 可能需要多步任务 |

### 三种典型的扩展形态

| 形态 | 例子 | 难度 | 风险 |
|---|---|---|---|
| **查询类**（读） | 查订单、查库存、查监控指标 | 低 | 低 —— 查错顶多是答错 |
| **计算/转换类**（无副作用） | 算价、换算单位、格式化 | 低 | 低 |
| **操作类**（写） | 下单、发通知、改配置、开关设备 | 中 | **高 —— 会真的改变世界** |

**建议顺序：先做查询类，跑稳了再做操作类。** 操作类必须额外加校验（见第 5 节）。

## 1. 扩展点，就这几处

第二阶段只会在这些地方动手，别的地方不用看（前六处是业务扩展点，后两处是横切能力，按需改）：

| 扩展点 | 位置 | 说明 |
|---|---|---|
| **① 工具注册** | `server/tools.py::build_tools()` | 唯一的注册中心。所有工具从这里交给框架 |
| **② 工具实现** | 按主题分模块（如 `sample_tools.py`） | 具体函数体，一个工具一个模块归属 |
| **③ 上下文** | `bot.py` 里的 `LLMContext` | 记忆注入、系统提示词 |
| **④ 结构化数据** | **框架不管** —— 自建（`memory.py`） | 数据库、业务表、会话/长期记忆 |
| **⑤ 知识库 / RAG** | **框架不管** —— 自建（`knowledge.py` + `embeddings.py`） | 文档切块 + 向量检索 |
| **⑥ 编排** | 框架自带 `flows/`（本仓库另有 `flows.py` 做固定调用链） | 多步任务、需要固定顺序的流程 |
| **⑦ 可信性护栏** | 自建（`guards.py`，挂在 `observers=`） | 检出「谎报执行」，可注入纠正让模型如实重答 |
| **⑧ 上下文摘要** | **框架自带**（`LLMContextSummarizer`，由 assistant 聚合器内部创建） | 在 `assistant_params` 里打开 `enable_auto_context_summarization` 即接线完成；阈值见 `settings.build_summarization_config()` |

**记住一句话**：框架给的是**接线板**，业务逻辑全在你的代码里。

## 2. 怎么加一个工具（核心，照着做）

### 2.1 三步骨架

以「查订单状态」为例，全部改动只在一个文件里（`server/tools.py` 或新建模块）。

> 下例假设 `_RESULT_PROPS` 已在模块顶部定义一次即可全局复用
> （见 `server/tools.py` 顶部；它是 `FunctionCallResultProperties(run_llm=True)`，
> 每个工具的 `result_callback` 都要带上它）。

```python
# ---------- 第 1 步：写处理函数 ----------
async def query_order(params: FunctionCallParams) -> None:
    args = params.arguments or {}
    order_id = str(args.get("order_id", "")).strip()

    row = memory.get_order(order_id)          # ← 你的业务逻辑（查库/调接口）

    if row is None:
        await params.result_callback(         # ← 失败也要回调，不要抛异常
            {"found": False, "spoken": f"没有查到订单 {order_id}"},
            properties=_RESULT_PROPS,         # ← 必须带
        )
        return

    await params.result_callback(
        {
            "found": True,
            "order_id": row["order_id"],
            "status": row["status"],
            # spoken：给模型直接照读的口语化说法，避免它把数字/编号念错
            "spoken": f"订单{row['order_id']}当前状态是{row['status']}",
        },
        properties=_RESULT_PROPS,
    )


# ---------- 第 2 步：定义 schema ----------
ORDER_SCHEMA = FunctionSchema(
    name="query_order",
    description=(
        "查询订单的当前状态和物流信息。"
        "当用户问「我的订单到哪了」「订单状态」「发货了吗」时调用。"
        "需要用户提供订单号；用户没给时先问清楚，不要猜。"
    ),
    properties={
        "order_id": {"type": "string", "description": "订单号，如 A20261001001"},
    },
    required=["order_id"],
    handler=query_order,          # ← 带 handler 会自动注册，无需手工 register_function
)


# ---------- 第 3 步：加进注册表 ----------
def build_tools() -> ToolsSchema:
    schemas = [
        CURRENT_TIME_SCHEMA,
        # ...
        ORDER_SCHEMA,             # ← 就加这一行
    ]
    return ToolsSchema(standard_tools=schemas)
```

**就这三步。** 前端不用改 —— pipecat 会把调用过程以 RTVI 消息推给官方前端。

### 2.2 handler 的四条硬规范

| 规范 | 原因 |
|---|---|
| **必须 `await params.result_callback(...)`** | 不回调 = 管线永远等不到结果，表现为「机器人不说话了」 |
| **必须传 `properties=_RESULT_PROPS`** | `run_llm` 默认是 `None`（假值），不传就**不会触发工具结果之后的那次 LLM 生成** —— 工具正常执行、日志有结果，但机器人永远不回答，**且完全静默** |
| **失败也要回调**，不要抛异常 | 抛出去会变成管线错误，用户那边就是「没反应」；用 `{"found": False}` + `spoken` 更可控 |
| **返回里带 `spoken`** | 让模型直接照读这句，避免它把 ISO 时间串、订单号念成一串数字 |

### 2.3 schema 的 description 怎么写（**决定模型会不会调**）

这是整个第二阶段**最花时间**的部分。写不好，模型就凭自己知识回答，根本不调你的工具。

必须写清**三件事**：

| 要写什么 | 例子 |
|---|---|
| **做什么** | 「查询订单的当前状态和物流信息」 |
| **什么时候该调** | 「当用户问『我的订单到哪了』『发货了吗』时调用」 |
| **什么时候不该调** | 「用户没提供订单号时先问清楚，不要猜」 |

第 3 条最容易被忽略，但**工具变多之后，边界比能力更重要** ——
两个描述重叠的工具会让模型选错。

### 2.4 参数设计原则

1. **少而正交**：一个工具做一件事。宁可两个工具，也不要一个带 `mode` 开关的万能工具。
2. **别让模型做算术/格式转换**：让它传原话，你在代码里解析。
   （如时间参数就让模型填「明天早上八点」，别让它算成时间戳）
3. **`required` 尽量小**：能不给必填就不给，让模型更容易调对。
4. **能用 `enum` 就用**：把可选项列出来，比让模型自由填字符串可靠得多。
5. **参数描述里给例子**：`{"type": "string", "description": "城市名，如「杭州」「北京」"}`。

### 2.5 通用查询 vs 专用工具

| 做法 | 何时用 |
|---|---|
| **一个通用查询工具**（表 + 条件 + 排序 + 聚合） | 表多、问题形态多（本仓库的 `query_data` 就是） |
| **一表一个工具** | 表少、或语义差别很大、需要特殊校验 |

本仓库选通用查询的原因：真实业务几十张表，一表一工具会**迅速撑爆提示词**，
而且模型还得先猜该用哪个。通用入口的组合能力是乘法级，工具数量是常数。

**代价**：模型需要知道表结构。所以 schema 的 description 里要带上表结构
（本仓库用 `memory.schema_summary()` 自动生成，改表不用同步改两处）。

## 3. 接数据：三种数据，三种接法

| 数据类型 | 例子 | 怎么接 | 本仓库状态 |
|---|---|---|---|
| **结构化** | 订单、指标、主机、告警 | 数据库 + 查询工具 | ✅ 已做（`memory.py`） |
| **长文档** | 手册、合同、知识文章 | 向量库 + 语义检索 | ✅ 已做（`knowledge.py` + `embeddings.py`；最小可用版，调优见第 10 节） |
| **实时外部** | 监控页、第三方 API | **采集脚本 + 落库**，工具只读库 | 部分（示例数据） |

### 3.1 关键设计：采集与查询必须分开

```
外部数据源 ──[采集脚本，定时跑]──→ 本地库 ──[工具，按需查]──→ 模型
```

**为什么要分开**：

- 工具是**同步等结果**的。如果工具里现去爬网页，用户就要多等几秒 —— 语音场景直接崩
- 外部源挂了，工具就失败。落库之后，工具查的是本地库，**外部故障不影响问答**
- 采集频率与问答频率解耦，各自调优

**这条边界也是给未来的自己省事**：换数据源时**只改采集脚本**，
工具、schema、提示词一行都不用动。

### 3.2 本仓库数据层的表（三类，共 6 张）

`server/memory.py`：

| 表 | 放什么 | 谁写 |
|---|---|---|
| `turns` | 会话历史（框架的短期记忆持久化） | `TurnRecorder`（**观察者**，挂在 `observers=`；两侧文本帧都会被各自聚合器消费，管线处理器收不到） |
| `facts` | 长期记忆（跨会话） | `remember_fact` 工具 |
| `metrics` / `hosts` / `alerts` / `orders` | 业务数据 | 采集脚本（当前是示例数据，见 `collect_orders.py`） |

### 3.3 加一张业务表的步骤

以「订单表」为例：

1. **建表**：在 `memory.py` 的 `_SCHEMA` 里加 `CREATE TABLE IF NOT EXISTS orders (...)`
2. **登记白名单**：加进 `TABLE_COLUMNS`（查询工具据此校验，模型碰不到白名单外的表）
3. **数值列**：若要做 avg/max/sum，加进 `NUMERIC_COLUMNS`
4. **写入函数**：加一个 `upsert_order(...)`，供采集脚本调用。
   订单号唯一，因此用 upsert 而非纯 insert —— 否则重跑采集会插入重复行
   （参考已有的 `record_metric` 是纯 insert，因为它按时间追加、本就不重复）
5. **采集脚本**：新增一个独立脚本，调 `upsert_order` 落数据
6. **测试**：`verify_tools.py --question "订单 A2026 到哪了"`，看工具有没有被调用、参数对不对

**不用改的**：`query_data` 工具、schema 描述（`schema_summary()` 自动带上新表）。

### 3.4 安全：不要让模型写 SQL

本仓库的做法是**只放行白名单内的表和列**，模型提交的是结构化参数
（`table` / `filters` / `order_by` / `aggregate`），由代码拼带占位符的语句。

实测：查不存在的表 `users`、不存在的列 `password`，都会被挡下并回报可用项。

**让模型自由写 SQL 等于把整个数据库的权限交给一个可能被诱导的模型。**
除非是只读的、隔离的、且能接受风险的场景，否则不要这么做。

## 4. 记忆：要做两层，只做一层不够

```
启动时 ──[注入上下文]──→ 模型「看得到」  ← 兜底
运行时 ──[工具读写]────→ 模型「查得到」  ← 精确
```

| 层 | 怎么做 | 作用 |
|---|---|---|
| **注入上下文** | `memory.load_memory_into_context(context)` | 启动时把所有事实塞进上下文，模型**一定看得到** |
| **工具读写** | `remember_fact` / `recall_fact` | 模型**主动**记、主动查，不受上下文长度限制 |

**为什么两层都要**：实测发现，当模型认为「自己能直接答」时，它**可能不调工具**。
- 只有工具层 → 它不调，就答「我不知道」
- 只有注入层 → 记忆一多就挤爆上下文
- **两层叠加 → 不调工具也能答对**（已验证：问「你还记得我叫什么名字吗」，
  未调工具，但答出了「记得，你叫张三」）

## 5. 编排：什么时候不能让模型自由决定

框架自带 `flows/`（原 pipecat-flows，已并入），本质是**对话状态机**。

| 场景 | 做法 |
|---|---|
| 单步查询 | 交给模型自由决定（允许它判断该不该调） |
| **多步任务**（A 的结果要喂给 B） | **用 `flows/` 显式编排**，不要指望模型自己串 |
| **写操作** | 加确认步骤 + 结果校验 |
| 有固定业务流程的 | 完全用 `flows/` 写死，模型只负责抽参数 |

**为什么不能指望模型自己串**：实测「先记住我住在杭州，再问『我这边天气怎么样』」，
模型**跳过了回想步骤**，自行填了「北京」并自信作答。工具调用了、格式也正常，
**只有内容是错的** —— 这类错误最隐蔽。

**写操作必须加校验**，因为存在「**谎报执行**」：
模型可能说「好的，已为你设置提醒」，而实际上**根本没调工具**。
对写操作，建议在管线里断言「回答声称完成了某动作 → 必须有对应的工具调用记录」，
否则拦截并改为诚实回答。

## 6. 测试方法（第二阶段的工程纪律）

> 这一节比代码更重要。**没有可靠的测量，就没有可靠的结论。**

### 6.1 三步测试流程

```bash
cd server

# ① 阳性对照：先确认环境是通的
uv run ../verify_tools.py --question "现在几点了"
#    ← 必须看到「[OK]   tool called」和**非空**的最终回答
#    ← 如果这里是「[ERR]  call failed」，说明是环境问题（欠费/网络），别往下测

# ② 单次验证：新工具能不能被正确调用
uv run ../verify_tools.py --question "订单 A20261001001 到哪了"

# ③ 重复统计：真实成功率是多少（关键，别只看一次）
for i in $(seq 1 20); do
  uv run ../verify_tools.py --question "订单 A20261001001 到哪了"
done
```

### 6.2 结论的四种情形必须分清

`verify_tools.py` 会输出**互斥**的四种结论：

| 输出 | 含义 | 排查方向 |
|---|---|---|
| `[OK]   tool called` | 正常 | —— |
| `[ERR]  call failed (API error)` | API 报错（欠费/限流/网络） | **环境**，不是模型 |
| `[ERR]  no answer (request failed / pipeline stuck)` | 请求没成功或管线卡住 | 环境/管线 |
| `[WARN] self-answered (no tool call)` | 模型判断不需要调 | **模型/提示词** |

**后两种的排查方向完全相反。** 把它们混在一起，会把环境故障读成模型问题
（本项目就把一次 `429 余额不足` 读成了「模型不调工具」，差点据此去换模型）。

### 6.3 两条铁律

1. **样本量为 1 的对比，得到的是噪声。** 缺省采样温度下模型每次结果不同，
   至少重复 5 次（建议 20 次）看分布。本项目曾用「各跑一次」的 A/B
   得出「工具越多越不调」，重测后被推翻。
2. **先确认测量工具是对的，再测被测对象。** 测量工具本身会有 bug，
   而它的 bug 会伪装成被测对象的问题。

### 6.4 工具是否被调用，看日志（不靠猜）

按 `HANDBOOK.md` 第 7 节：日志里能看到**六个时刻**的完整记录 ——
模型要求调用 / 开始执行 / 完成 / 失败 / 超时 / 取消，含参数、结果、耗时。
工具没被调、调错了、调了但失败，都能一眼看出来。

## 7. 第二阶段已知的坑

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | `_RESULT_PROPS` 忘传 | 工具执行了但机器人不回答，**完全静默** | 每个工具都传 |
| 2 | **谎报执行** | 没真做却说做了，用户基于虚假状态决策 | 提示词禁止 + 输出校验 |
| 3 | 多步任务指望模型自己串 | 跳步 + 自行编造参数，**内容错但看起来正常** | 用 `flows/` 显式编排 |
| 4 | 工具描述没写「什么时候不该调」 | 工具多了容易选错 | description 写清边界 |
| 5 | 工具里现去调外部接口 | 用户多等几秒，语音场景崩 | **采集与查询分开**，工具只读本地库 |
| 6 | 让模型写 SQL | 数据库权限失控 | 白名单 + 结构化参数 |
| 7 | 只看一次测试就下结论 | 把噪声当规律 | 重复 5~20 次看分布 |
| 8 | 把环境故障读成模型问题 | 换错方向，白折腾 | 先跑阳性对照；区分四种失败 |
| 9 | 工具内部重复打日志 | 同一件事记两遍，噪音 | 权威记录交给 `FunctionCallObserver` |
| 10 | 有状态工具用**模块级/全局变量**存状态 | 多会话时串数据（A 的提醒算进 B 的计数），且会无上限增长 | 状态**按会话绑定**：`build_tools(session_id)`，见 `sample_tools.reminder_schema` |
| 11 | 工具 handler **抛异常**（如 `limit` 传成 `"十条"`） | 工具「跑了」但没有结果回到模型，**机器人永不回答**（与忘了 `run_llm=True` 同一类静默失败） | `build_tools()` 用 `safe_handler` **统一包装**所有 handler：记 traceback + 回 `ok=False`，机器人如实说"出错了" |
| 12 | 知识库写入侧拿**调用时的原样路径**当文档标识 | 同一文件灌两次变两篇 → 检索返回重复正文块；`--delete` 必须拼写完全一致 | 标识统一取「相对仓库根的路径」；并加 `--prune` 清掉源文件已删的记录（否则会检索到已删除的内容） |
| 13 | 基准脚本的**基线**不是「实际在跑的配置」，或注释说要扫的变量其实没扫 | 数字看着合理，却在和一个没人用的配置对比（如 `asr_bench` 曾拿 `language=None` 当基线）；声称已修的调参从未被测量 | 基线必须等于 `settings.py` 实际下发的参数；注释里写的变量要真出现在循环里；`verify_stack` 对已知 5 秒陷阱改为 WARN 而非沉默 |

## 8. 完整示例：加一个「查订单」工具（端到端）

假设要把订单系统接进来。

**① 建表**（`memory.py` 的 `_SCHEMA` 里加）

```sql
CREATE TABLE IF NOT EXISTS orders (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id   TEXT NOT NULL UNIQUE,
    customer   TEXT NOT NULL DEFAULT '',
    status     TEXT NOT NULL DEFAULT '待发货',
    amount     REAL NOT NULL DEFAULT 0,
    updated_at REAL NOT NULL
);
```

**② 登记白名单**（同一个文件）

```python
TABLE_COLUMNS["orders"] = ["order_id", "customer", "status", "amount", "updated_at"]
NUMERIC_COLUMNS["orders"] = ["amount"]
```

**③ 采集脚本**（新文件 `collect_orders.py`，独立于 bot 运行）

```python
"""定时从订单系统把数据拉到本地库。工具只读本地库，不直接调外部接口。"""
import memory

def sync():
    memory.init_db()
    for item in fetch_from_your_system():      # ← 换成你的真实来源
        memory.upsert_order(
            order_id=item["order_no"],
            customer=item["buyer"],
            status=item["state"],
            amount=float(item["total"]),
        )
```

**④ 工具**：因为 `query_data` 是通用的，**这一步不需要新写工具** ——
模型可以直接 `query_data(table="orders", filters={"order_id": "..."})`。

**⑤ 提示词/schema**：`schema_summary()` 会自动把 `orders` 表带进工具描述。

**⑥ 测试**：

```bash
uv run ../verify_tools.py --question "订单 A20261001001 现在什么状态"
uv run ../verify_tools.py --question "这个月一共多少笔订单"
```

**⑦ 回归**：`uv run bot.py`，用语音问一遍，确认端到端可用。

> **注意第 ④ 步** —— 这就是通用查询工具的价值：**加表不用加工具**。
> 只有当某类查询需要特殊校验、或语义与通用查询差别很大时，才另写专用工具。

## 附：一句话总结

**第一阶段是「把管道接通」，第二阶段是「往管道里灌业务」。**

框架只提供接线板（工具注册、上下文、编排）；
**数据怎么存、工具怎么写、什么时候不该让模型自由决定** —— 全是你的活，
也正是换框架带不走的部分。
