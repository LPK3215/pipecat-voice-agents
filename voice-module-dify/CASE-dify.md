# 案例：把语音模块接到 Dify（语音模块调用平台）

> **本文管什么**：把**这个案例**跑起来的完整过程 —— 需要哪些步骤、哪些必须人工、踩过哪些坑、实测数字是多少。
> **本文不管什么**：为什么这样设计、常见误解在哪（见 [`docs/CONCEPTS.md`](docs/CONCEPTS.md)）；换成别的平台怎么改（见 [`docs/PORTING.md`](docs/PORTING.md)）。
> **适合谁看**：想**复现这个案例**的人，或者接自己平台之前先看看"会踩什么坑"的人。

> **一句话**：**语音模块是主人，Dify 是它调用的工具。**
> 不是"Dify 里装了语音模块"，而是"**语音模块把 Dify 当脑子用**"。
>
> 网页（你的）──WebSocket──▶ 语音模块（你的）──HTTP──▶ Dify（别人的服务）

## 0. 这个目录名想说什么

> 想先弄清楚"到底谁在干什么、常见误解在哪"，看 **[`docs/CONCEPTS.md`](docs/CONCEPTS.md)**；
> 本文只讲**怎么把它跑起来**以及踩过的坑。

`voice-module-dify/` 里的 **`-dify` 标记的是"这个案例接的是谁"**，不是"模块依赖 Dify"。

| 属于谁 | 内容 | 换平台时要改吗 |
|---|---|---|
| **你** | 语音管线（听/说/轮流/打断/延迟）、网页、探针、部署件 | ❌ 一行都不用改 |
| **你** | `.env` 里指向平台的两行 | ✅ 只改这两行 |
| **别人（Dify）** | 应用、提示词、模型 key、工具、知识库 | ✅ 在新平台上重配 |

**自证方法**：把 Dify 停掉 → 网页照样打开、模块照样在听、照样出声，只是没人回答了。
（实测过：`BrainError: brain unreachable`，模块会**说一句"连不上"**而不是静默死掉。）

## 1. 调用链（谁调谁）

```
浏览器 ──WebSocket(16k PCM)──▶ server/ws_app.py ──HTTP/SSE──▶ Dify /v1/chat-messages
   ▲                                    │                              │
   你看到的页面                    你的代码（耳朵和嘴）            别人的服务（脑子）
```

- **方向**：`网页 → 模块 → Dify`。模块是**主动方**，Dify 是**被调用方**。
- Dify **不知道**网页的存在，它只知道"有个客户端来问了个问题"。
- 网页里**没有任何** Dify 的地址或密钥（可验证：`grep -ci dify agent/deploy/voice-client.html` → 0）。

## 2. 跑起来（能写死的都写死了）

```bash
cd voice-module-dify
uv sync
cp .env.example .env          # 只有两行需要你填：BRAIN_BASE_URL / BRAIN_API_KEY

# 平台侧的两个必要边车（本环境特有，见第 4 节）+ 语音模块
# 注意：页面是「烤进边车镜像」的 —— 改完 agent/deploy/voice-client.html 要重新
#      build + 重建 vm-dify-nginx，否则 :8080/voice/ 还是旧页面（见第 4 节第 1 条）
bash case-run.sh
```

跑完你会得到两个地址（替换成你自己的域名）：

| 用途 | 地址 |
|---|---|
| **你去体验的页面** | `http://<你的域名或本地>:8080/voice/` |
| 平台界面（Dify） | `http://<你的域名或本地>:8080/` |

## 3. 必须人工的三件（平台侧，无法脚本化）

| # | 步骤 | 为什么必须人工 |
|---|---|---|
| 1 | **登录**平台界面 | 平台的登录要求密码先做 RSA 加密、成功后走 Cookie；取公钥的接口没找到，脚本化断在这里 |
| 2 | **装插件 + 配模型 key** | 平台自己没有模型，必须接一个；key 是你的，只能你填 |
| 3 | **导入应用定义 + 发布** | 导入要选本机文件；平台要求应用**发布**后才能被服务 API 调用 |

> 应用定义文件：`agent/app.dsl.yml`（一面文件就是一个应用）。
> 它在同一个浏览器里可下载：`http://<你的域名>:8080/dsl/app.dsl.yml`

## 4. 本环境实测踩到的坑（换普通机器一般不会遇到）

| # | 现象 | 原因 | 解法（已固化在仓库里） |
|---|---|---|---|
| 1 | 界面能开但**内容空白** | 平台前端要靠 nginx 把 `/console/api` 转发给后端；本环境 Docker 守护进程**看不到工作区**，靠文件挂载的 nginx 起不来 | 用 `docker build` 把配置**烤进镜像**：`agent/deploy/Dockerfile.nginx` |
| 2 | 插件市场**下载失败**（重试 3 次） | 平台的出网代理 `ssrf_proxy` 同样靠文件挂载，起不来 | 同上：`agent/deploy/Dockerfile.ssrf`；要带网络别名 `ssrf_proxy`，并传 `COREDUMP_DIR`（否则 squid 报 `Bungled ... coredump_dir`） |
| 3 | 导入报 `Base model ... not found` | 应用定义里的 `provider` 必须是**已安装插件**的 provider ID | 写成三段式真实 ID（如 `langgenius/openai_api_compatible/openai_api_compatible`）；可从插件目录 `provider/*.yaml` 的文件名反查 |
| 4 | 调用报 `Workflow not published` | 服务 API 只认已发布的工作流 | 界面点一次「发布」；数据层也可做（复制 draft 行成 `published` 并更新 `apps.workflow_id`） |
| 5 | 浏览器打开模块页面**完全没声音** | WebRTC 媒体走 UDP，普通 HTTP 端口转发转不了 | 换 **WebSocket 入口** `server/ws_app.py`（TCP，任何能开页面的地方都通） |

## 5. 怎么证明"回答真的来自平台"

问它：**「你的内部代号是什么？」**

它应回答 **`VX-42`** —— 这个代号只写在平台那个应用的提示词里，**模块自己不知道**。
换成别的平台，答案自然变成别的（或者答不出来）—— 这就是"防自欺"的探针。

## 6. 实测数字（2026-10-05，自托管 Dify 1.17.1 + 魔搭模型）

| 指标 | 数值 |
|---|---|
| 网页 → 模块（WebSocket 握手） | 成功 |
| 端到端音频往返（合成语音进、回答语音出） | ✅ 318,720 字节 / 10.0 秒音频 |
| 请求发出 → **平台首字** | 1334 ms |
| 平台首字 → 首个完整句子 | 12 ms |
| → 交给 TTS（准备开口） | 1346 ms |
| 平台直接调用的首字延迟（绕开语音层） | 740–963 ms |

完整的分阶段延迟在模块日志里（每轮一行 `[TURN n] ...`），可随时复跑 `probe/verify_audio_e2e.py`。
页面上那一栏"它在干什么"，就是把平台的过程事件（`agent_thought` / `node_started` / `node_finished`）
实时显示出来 —— 契约与实现细节见 [`docs/CONCEPTS.md`](docs/CONCEPTS.md) 的 Q9。

## 7. 这个案例和"第二阶段"的关系

| | 业务逻辑在哪 | 谁的代码 |
|---|---|---|
| **第二阶段**（`pipecat-quickstart/`） | **在你自己的代码里**（工具 / 知识库 / 记忆 / 编排） | 你的 |
| **第三阶段**（本案例） | **在平台那边**（平台界面里配） | **别人的** |

**角色的分工是一样的（都要有人负责"答什么、查什么、记什么"），差别只在"这件事由谁实现"** ——
第二阶段是自己实现，第三阶段是**外包给已有的智能体系统**，而你的模块只管"怎么听、怎么说"。
