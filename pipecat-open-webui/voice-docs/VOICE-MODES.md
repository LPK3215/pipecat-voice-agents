# 语音形态选择与实现指南（VOICE-MODES）

> **本文解决一个问题**：你到底要哪种语音？**怎么选？怎么实现？**
>
> 以后想在本项目（或**任何宿主系统**）里实现某种语音形态时，先读这一篇。
> 相关：[`INTEGRATION.md`](INTEGRATION.md)（本项目实际做了什么）｜ [`PLATFORM-SELECTION.md`](PLATFORM-SELECTION.md)（宿主选型）
>
> ⚠️ **更正记录（2026-10-05）**：初版把语音分成"两种"，实际应分**三档**。
> 关键更正：**③ Open WebUI 已经能"连续对话"**（通话模式是自动循环），差的只是**精细度**，不是"能不能"。

## 1. 三档（不是两档）

| | **A. 简单 I/O** | **B. 连续对话** | **C. 精细实时** |
|---|---|---|---|
| 像什么 | 按一下说一句 | **像打电话**：自动循环 | B + 像面对面 |
| 交互 | 手动，每次点麦克风 | 说完自动答，答完自动听 | 同上，且**一说话就能打断** |
| **打断方式** | 无 | **点击按钮** | **语音**（barge-in） |
| 延迟要求 | 低 | 中（能接受等待） | 高（盯着"首句就开口"） |
| 额外功夫 | —— | **自动循环** | 语音打断 / 首句开口 / 填场 / 流式 |
| 谁有 | —— | ✅ **③ `pipecat-open-webui`** | ✅ **② `voice-module-dify`** |
| 参考位置 | —— | 前端 `src/lib/components/chat/MessageInput/CallOverlay.svelte`（自动循环） | `voice-module-dify/server/brain.py`（5 机制） |

> **关键结论**：**③ 和 ② 都能"连续对话"** —— 差别不是"能不能"，而是 **C 比 B 多四层功夫**。

## 2. 怎么选（判断标准 —— 这就是"选择方式"）

| 你的需求 / 条件 | 目标档 | 怎么做 |
|---|---|---|
| 能语音输入输出就行 | **A** | ③ 现状，见 [`INTEGRATION.md`](INTEGRATION.md) |
| 像打电话、能连续说 | **B** | **③ 已经有**（进"通话"模式即可） |
| 像打电话 + **"你一说话她就停"** | **C** | 参考 ②；在 ③ 上要补第 4 节那四层 |
| 宿主架构固定、不想大改它 | A 或 B | 用它已有的 |
| 宿主是**可插拔管线**（Pipecat） | C 直接做 | 参考 ② |

**判断口诀**（两步）：

1. **有没有"自动循环"**（说完自动答、答完自动听）？ → 有 = **B**
2. **有没有"语音打断 / 首句就开口 / 填场"**？ → 有 = **C**

---

## 3. 形态 C 的 5 个机制（② 已跑通并验证）

> **任何宿主**要做 C，都要解决这 5 件事。

| # | 机制 | 为什么必须 | ② 的参考代码 |
|---|---|---|---|
| 1 | **轮次判定**（谁在说 / 说完没有） | 平台**从不听音频**，必须由语音层判断"用户说完了"再把文字交出去 | `../../voice-module-dify/server/brain.py:112`（`on_user_turn_stopped`） |
| 2 | **首句就开口**（不等答完） | 平台是网络往返，等全文 = 加上它整段生成的时间 | `brain.py:151-162`（按句切分、流式喂 TTS） |
| 3 | **填场**（平台慢时先说一句） | 静默几秒，用户会以为坏了 | `brain.py:206-215`（多条台词随机轮换） |
| 4 | **打断 barge-in**（双向停） | 用户插话要**立刻停播 + 通知平台停止生成** | `brain.py:103-110`（本地停）、`218-228`（通知平台 `stop`） |
| 5 | **过程可见**（思考 / 工具事件） | 否则"它在想"和"它卡住了"看起来一模一样 | `brain.py:82-95`（用 **urgent 帧**，否则会被 TTS 暂停挡住，实测晚 ~16s） |

**三个技术前提**（缺一个就做不了 C）：

1. **能流式** —— 平台/LLM 边生成边返回（否则"首句就开口"无从谈起）
2. **能拿到"用户说完"事件** —— VAD + 轮次
3. **打断能双向停** —— 本地停播 **+** 告诉对方停生成

---

## 4. 在 ③ 上从 B 升到 C，要补哪几层

**不是"重做 ② 的核心"，是补四层**（主要在**前端**，后端只加一个流式端点）：

| # | 要补的 | 在哪 | 说明 |
|---|---|---|---|
| 1 | **语音打断** | 前端 `CallOverlay.svelte` | 它本来就有 VAD（用于判停录音），**复用它**：检测到用户说话 → `speechSynthesis.cancel()` 停播 |
| 2 | **流式 STT** | 后端 `routers/audio.py` 加 WS 端点 | 现在是"整段录完再传"，流式后延迟明显下降 |
| 3 | **首句就开口** | 前端流式播放 | 现在等完整回复再 TTS；改成**按句播** |
| 4 | **填场** | 前端（或后端） | 等待超过 N 秒先说一句 |

**代价**：以**改前端为主** + 后端加一个端点。**远小于**"重写一个 ②"。

---

## 5. 结论

| 你想要 | 现状 |
|---|---|
| 简单 I/O（**A**） | ✅ ③ 已实现 |
| **连续对话（B）** | ✅ **③ 已实现**（通话模式：自动循环 + 点击打断） |
| **精细实时（C）** | ✅ ② 已实现；③ 要补第 4 节那四层 |
| 想在新宿主上做 C | 先确认宿主**能否流式 + 有无轮次事件**；不能 → 成本会很高 |

**一句话**：**A / B / C 是三个档位，不是"能不能"的开关。**
**③ 已经站在 B 档** —— 这正是本项目要验证的："在一个很大的系统里，语音能以这种方式接进来并使用" —— **答案是能。**
