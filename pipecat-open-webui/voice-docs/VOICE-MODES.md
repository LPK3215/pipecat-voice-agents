# 语音形态选择与实现指南（VOICE-MODES）

> **本文解决一个问题**：你到底要哪种语音？**怎么选？怎么实现？**
>
> 以后想在本项目（或**任何宿主系统**）里实现某种语音形态时，先读这一篇。
> 相关：[`INTEGRATION.md`](INTEGRATION.md)（本项目实际做了什么）｜ [`PLATFORM-SELECTION.md`](PLATFORM-SELECTION.md)（宿主选型）

---

## 1. 两种形态（先分清，别混）

| | **形态 A：简单语音 I/O** | **形态 B：实时语音对话** |
|---|---|---|
| 像什么 | 对讲机的"按一下说一句" | **打电话**（边走边说、随时打断） |
| 交互 | 一问一答（回合制） | 连续、可插话 |
| 延迟要求 | 低（能接受几秒） | 高（盯着"首字/首句"） |
| 复杂度 | **低 —— 薄薄一层 I/O** | **高 —— 轮次 / 打断 / 填场 / 延迟** |
| 本项目（③）现状 | ✅ **已实现** | ❌ **未做** |
| 参考实现 | **③** `pipecat-open-webui` | **②** `voice-module-dify` |

---

## 2. 怎么选（判断标准 —— 这就是你说的"选择方式"）

| 你的需求 / 条件 | 选 |
|---|---|
| 只要"能语音输入、能语音输出" | **A** |
| 要"像打电话一样自然，能打断" | **B** |
| 宿主系统架构固定（如 Open WebUI），**不想大改它** | **A** |
| 宿主是**可插拔管线**（如 Pipecat），能往中间插处理器 | B 可以直接做 |
| 人手 / 时间有限，先跑通为主 | **A** |
| 愿意处理打断、回声、抖动、轮次误判 | B |

**一句话记法**：

> - **A = 给系统装上"嘴和耳朵"**（只需在输入/输出两端加钩子）
> - **B = 给系统装上"实时对讲机"**（还要处理"什么时候该说、被打断怎么办"）

**判断口诀**：**先问宿主"能不能流式、有没有'用户说完'事件"。**
能 → 可以上 B；不能 → 只做 A，或先改宿主。

---

## 3. 形态 B 的实现要点（5 个机制 —— 可迁移）

> 这是 **② 已经跑通并验证过**的做法。**任何宿主**想做 B，都要解决这 5 件事。

| # | 机制 | 为什么必须 | ② 的参考代码 |
|---|---|---|---|
| 1 | **轮次判定**（谁在说 / 说完没有） | 平台**从不听音频**，必须由语音层判断"用户说完了"再把文字交出去 | `../../voice-module-dify/server/brain.py:112`（`on_user_turn_stopped`） |
| 2 | **首句就开口**（不等答完） | 平台是网络往返，等全文 = 加上它整段生成的时间 | `brain.py:151-162`（按句切分、流式喂 TTS） |
| 3 | **填场**（平台慢时先说一句） | 静默几秒，用户会以为坏了 | `brain.py:206-215`（多条台词随机轮换） |
| 4 | **打断 barge-in**（双向停） | 用户插话要**立刻停播 + 通知平台停止生成** | `brain.py:103-110`（本地停）、`218-228`（通知平台 `stop`） |
| 5 | **过程可见**（思考 / 工具事件） | 否则"它在想"和"它卡住了"看起来一模一样 | `brain.py:82-95`（用 **urgent 帧**，否则会被 TTS 暂停挡住，实测晚 ~16s） |

**三个技术前提**（缺一个就做不了 B）：

1. **宿主能流式** —— 平台/LLM 必须"边生成边返回"（否则"首句就开口"无从谈起）
2. **语音层能拿到"用户说完"事件** —— VAD + 轮次判定
3. **打断能双向停** —— 本地停播 **+** 告诉对方停生成

---

## 4. 想在**本项目（③ Open WebUI）** 上做形态 B，需要什么

**诚实说：不是"配置一下就行"。**

| 障碍 | 说明 |
|---|---|
| ❌ 没有可插拔管线 | Open WebUI 的语音是**固定流程**：前端录音 → **整段上传** → 转写 → 朗读 |
| ❌ 没有流式 STT | 它是"录完一整段再识别"，不是边说边识别 |
| ❌ 没有轮次 / 打断 / 填场钩子 | 这些得自己加 |

**要做的话**（按投入从大到小）：

1. 前端 `src/lib/components/chat/MessageInput/CallOverlay.svelte`：改成**连续推流**（而非整段录制）
2. 后端 `backend/open_webui/routers/audio.py`：**新增音频 WebSocket 端点**（流式 STT）
3. 新增一个 **轮次/打断/填场处理器**（可参考 ② 的 `brain.py`）
4. 前端改成**流式播放 + 可打断**

> **结论**：在 ③ 上做 B ≈ 把 ② 的核心重做一遍，投入**远大于** A。

---

## 5. 结论（该用哪个）

| 你想要 | 用哪个 | 现状 |
|---|---|---|
| 简单的语音输入 / 输出 | **③ `pipecat-open-webui`** | ✅ 已实现（见 [`INTEGRATION.md`](INTEGRATION.md)） |
| **实时语音对话（像打电话）** | **② `voice-module-dify`** | ✅ 已实现（brain 层 5 机制） |
| 想在**新宿主**上做 B | 先确认宿主**能否流式 + 有无轮次事件** | 不能 → 成本会很高 |

**一句话**：**A 和 B 是两种东西，不是一个东西的两个档位。**
A 是"把语音接进系统"，B 是"把语音接进系统**并让它实时对话**" —— 后者要多解决 5 个问题。
