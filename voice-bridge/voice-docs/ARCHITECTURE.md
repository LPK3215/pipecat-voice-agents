## 1. 目标（一句话）

**让一个已经存在的大系统，用最小改造获得"能听会说"的能力** —— 语音只是它的一个部件，
不是它的主体；大系统自己不因为接入语音而改变架构。

由此推出三条硬约束：

1. **反向调用**：**大系统 A 调用 B** ✓（不是 B 去调 A ✗）。A 需要语音时才叫 B，不需要时 B 完全可以不在场。
2. **B 不做思考**：回答什么、记什么、查什么**都在 A 里** ✓。B 只把"听到的文本"交给 A，把"A 给的文本"念出来 ✓。
   这一条让 B 的接口极窄 ✓ —— 窄接口才能"插入"别人的系统 ✓。
3. **多会话**：A 里可能有多个用户/多个任务同时用语音 ✓ → 会话必须隔离、可并发、可单独关闭 ✓。

## 2. 两种拓扑（为什么不能照搬②）

| | ②`voice-module-dify` | ③本项目 |
|---|---|---|
| 图 | `网页 → 语音模块 → 平台` | `大系统 A → 语音组件 B` |
| B 的位置 | 链条上的**第二环**，它决定何时问、何时说 | **一个零件**，A 决定何时用 |
| 谁常驻 | B 常驻（它就是服务） | A 常驻；**B 可以是按需拉起/多实例** ✓ |
| 会话数 | 1（一个人对着网页说） | N（A 里的多个会话） |

**结论**：②的**内部**（管线、事件通道、打断/填场/分句）可以直接复用 ✓；
②的**外壳**（单会话、主动去调平台、没有鉴权）**不能复用** ✗，必须新写 ✓。

## 3. 接口契约（A → B）

约定：`Authorization: Bearer <token>`（见第 5 节），请求/响应都是 JSON，时间为毫秒。

### 3.1 开一个语音会话

```
POST /v1/sessions
  { "locale": "zh-CN",            // 可选：识别/合成的语言
    "metadata": { … } }           // 可选：A 自己的标识（用户 id、任务 id…），B 只存不解释
→ 201 { "session_id": "s_…",
        "audio_ws": "/v1/sessions/s_…/audio",
        "expires_at": 1730000000000 }
```

### 3.2 音频通道（双向）

```
WS /v1/sessions/{id}/audio
  客户端 → B：二进制帧 = 16-bit 单声道 PCM（16 kHz，小块发送）
  客户端 → B：文本帧   = { "type": "barge_in" }        // 可选：A 侧要求立刻停
  B → 客户端：二进制帧 = PCM 音频
  B → 客户端：文本帧   = 事件（第 4 节）
```

> 这套"**二进制＝音频、文本＝事件**"的约定是从②**直接搬**的 ✓ —— 它已经在真实环境验证过 ✓
> （含"框架自己也在同一 socket 上发消息，客户端只认自己认识的 `kind`"这条坑 ✓）。

### 3.3 让它主动说一句（②没有的能力）

```
POST /v1/sessions/{id}/say
  { "text": "您有一条新工单。", "interrupt": false }
→ 202 { "utterance_id": "u_…" }
```

A 播报时**不需要**先给音频通道推流 ✓；B 自己合成、自己按会话排进播放队列 ✓。
`interrupt: true` 表示"打断当前这句、立刻说这句" ✓。

### 3.4 关掉

```
DELETE /v1/sessions/{id}   → 204
```

关闭后：通道断开、队列清空、资源释放 ✓。会话也可以因闲置超时自动关闭 ✓（上限见第 5 节）。

### 3.5 错误（统一形状，别让 A 猜）

```
4xx/5xx { "error": { "code": "session_not_found",
                     "message": "…人话…",
                     "retryable": false } }
```

## 4. 事件（B → A，文本帧）

沿用②的词表 ✓（同一个 `kind` 语义，A 侧不用再学一套 ✓）：

| kind | 含义 |
|---|---|
| `state` | `listening` / `thinking` / `speaking` |
| `user` | 识别出的用户话（A 拿它去思考 ✓） |
| `say` | B 正在念的内容（含填场语 ✓） |
| `timing` | 这一轮耗时拆解（三段：听到 / 首字 / 开口 ✓） |
| `error` | 出错原因（**不静默** ✓） |
| `interrupt` | 被打断 |

**A 怎么拿到"该回什么"**：A 订阅 `user` 事件 ✓ → 自己去思考（它的模型、它的工具、它的记忆 ✓）→
把结果交给 `POST /say` ✓ 或**流式**交给一个对应的 `POST /v1/sessions/{id}/say/stream`（分批字 ✓，推荐 ✓，
语音场景必须流式 ✓ —— 与②当年的结论一致 ✓）。

## 5. 会话模型、隔离与限额

| 项 | 设计 | 理由 |
|---|---|---|
| 隔离 | 每会话独立的状态机与播放队列 | 两路音频**绝不能串** ✗（这条要有探针 ✓） |
| 鉴权 | `Bearer` token，可撤销 | A 可能多租户 |
| 闲置超时 | 默认 5 分钟 | 防止 A 忘记关 |
| 单会话上限 | 时长 / 并发各一个上限 | 防止一个坏会话吃掉整机 |
| 会话数上限 | 明确的数字 + 排队或拒绝（**不要静默丢弃** ✗） | 让 A 能感知压力 |

## 6. 部署形态（待定，见第 8 节）

| 形态 | 优点 | 缺点 |
|---|---|---|
| **一个进程多会话** | 省内存（语音模型只加载一份 ✓）、实现最简单 | 一个会话崩了可能影响别人；模型抢占 CPU |
| 每会话一个进程 | 隔离彻底 | 每个进程都加载模型（Whisper/Piper 一份几百 MB ✗） |

**建议**：先做"**一个进程多会话**" ✓（够用、能验证 ✓），把隔离做成逻辑隔离 ✓；
真要强隔离再按会话分实例 ✓。

## 7. 与 `voice-module-dify` 的关系：能搬什么、要新写什么

| | 内容 | 处置 |
|---|---|---|
| ✅ 直接搬 | PCM 契约与序列化器、事件词表与紧急帧那条坑、打断/填场/分句旋钮、时间线、探针写法 | 复用（注意：搬的是**经验与形状** ✓，代码可整体拷过来再改 ✓） |
| 🔧 要新写 | 会话管理（多会话、超时、限额）、鉴权、`/say` 主动播报、HTTP 外壳、并发下的资源争用 | 本项目的核心工作量 ✓ |
| ❌ 不要 | "B 主动去调平台"的那套（`agent_client` / `conversation_id`） | 本项目里**调用方向相反** ✓，思考归 A ✓ |

> 另外记住②的两个教训：**事件必须用 urgent 帧**（否则被 TTS 暂停挡住、晚十几秒 ✗）；
> **平台/宿主的登录往往不能脚本化** ✓ —— 接入 A 时会遇到同类问题 ✓。

## 8. 待你定的 4 件事（定了我就能写实现）

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | **大系统 A 怎么调 B** | (a) 普通 HTTP 服务（A 里一个后端调它）· (b) 工作流平台的一个节点（如 Dify / n8n / 低代码）· (c) 消息队列/事件总线（松耦合） | 先按 **(a)** 定 ✓ —— 接口最通用，之后包一层就能变成 (b)(c) ✓ |
| 2 | **音频从哪来** | (a) 浏览器网页 · (b) 电话（SIP/网关）· (c) A 自己的音频流（已有麦克风设备/已录好的音频） | 先按 **(a)** 定 ✓（最容易验证 ✓）；电话/录音之后换传输层 ✓ |
| 3 | **鉴权** | (a) 静态 Bearer token · (b) 与 A 的登录体系对接（JWT 校验）· (c) 内网不鉴权（仅本地测试） | 先 **(a)** ✓，接口留出 (b) 的位置 ✓ |
| 4 | **是否复用②的代码** | (a) 拷贝相关模块再改 · (b) 把②的核心抽成包、两边共用 · (c) 全部重写 | 先 **(a)** ✓（快、能验证 ✓）；等这个"组件形态"真的成立，再考虑 (b) ✓ |
